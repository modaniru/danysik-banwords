> в GHCR; SSH-деплой удалён. Первичный запуск через Coolify — отдельный шаг.


Планируемые изменения сервиса — в [BACKLOG.md](BACKLOG.md), выполненные —
в [COMPLETED.md](COMPLETED.md).

Backend SayPatch на **Go 1.27.1**, только стандартная библиотека. Единственный
источник функциональных данных — [`data/catalog.json`](data/catalog.json) в Git.
Он содержит все 22 текущих правила, варианты замен, категории и явные режимы.
Внутри Docker-сети сервис слушает 8080; маршруты Coolify описаны в `coolify.json`.

## API

Контракт — [`openapi.json`](openapi.json), версия API **2.0.0**.
При любом изменении хендлеров одновременно обновлять OpenAPI и тесты.
Спецификацию можно получить JSON-запросом; отдельной HTML-справки нет.

| Метод | Путь | Ответ и доступ |
| --- | --- | --- |
| GET | `/api/banwords/catalog` | Полный функциональный каталог; только service-токен |
| GET | `/api/banwords/catalog/hash` | `{"hash":"64 lowercase hex"}`; только service-токен |
| GET | `/api/banwords/openapi.json` | OpenAPI JSON; service-токен либо сессия с правом чтения |
| GET | `/healthz` | Внутренняя готовность, 204; наружу не проксируется |

Каталог имеет формат `saypatch-rules`, `version: 1`, общий массив `variants`
и массив `rules`. Каждое правило содержит ровно пять обязательных полей:

| Поле | Назначение |
| --- | --- |
| `word` | Исходное слово |
| `category` | `safe` или `banword` |
| `variantIds` | Индексы вариантов из массива `variants` |
| `matchMode` | `word` — целое слово; `substring` — поиск внутри слова |
| `replaceMode` | `word` — заменить содержащее слово целиком; `match` — только совпавший фрагмент |

В текущем наборе safe-правило «Денчик» и исключение «жид» ищутся как целые
слова; остальные банворды — внутри слова. Во всех текущих правилах явно задана
замена содержащего слова целиком. Этот перенос не пересматривает состав или
политику поиска; отдельный пересмотр каждого банворда остаётся BWS-1.
Локальные настройки клиента в каталоге не хранятся. Закрытая схема отклоняет
неизвестные поля как на верхнем уровне, так и в каждом правиле.

Лимиты: один файл до 64 КиБ, итоговый JSON-ответ тоже до 64 КиБ, до 50 правил,
2500 вариантов и 50 ссылок на варианты в одном правиле. Строковые лимиты
совместимы с JS-клиентом: исходное слово до 50 UTF-16 единиц, вариант до 100.
Сервис сохраняет исходные строки и функциональные поля; текст сообщений
сервису не передаётся.

## Проверка свежести

При запуске сервис читает `catalog.json`, проверяет его и строит стабильное
тело ответа через `json.Marshal`: ключи объектов упорядочены, отступы удалены.
SHA-256 вычисляется по **точным байтам всего этого тела**. Значения всех полей,
порядок правил и порядок вариантов входят в хэш. Изменение отступов или
порядка ключей исходного JSON хэш не меняет.

`GET /catalog` возвращает эти байты без повторного JSON-кодирования и заголовок
`ETag: "<64 hex>"`. `GET /catalog/hash` возвращает тот же хэш без кавычек ETag
в объекте `{hash}`. Клиент может сначала проверить свежесть и предложить
обновление полного набора. Для проверки целостности нужно хешировать полученные
байты тела, а не заново сериализованный объект. Условный GET/304 не используется;
ответы имеют `Cache-Control: no-store`.

История изменений хранится обычными коммитами Git. Рабочий файл один:
`data/catalog.json`. Для обновления изменить его, проверить и отправить новый
коммит; бинарник и образ включают новый каталог через `go:embed`.

## Доступ и токены

1. Суперадмин выдаёт пользователю `banwords`, `banwords:tokens` и
   `banwords:dictionaries:read` с промежуточным узлом `banwords:dictionaries`.
   Новым пользователям доступ автоматически не выдаётся.
2. Пользователь входит на сайте через Twitch и создаёт service-токен на
   `/banwords/`. Secret `bw_…` показывается один раз; auth хранит SHA-256.
   Срок 1–90 дней, по умолчанию 90; максимум 20 активных токенов.
3. Клиент отправляет `Authorization: Bearer bw_…` в Caddy. Auth проверяет
   токен, срок, отзыв и актуальные права, затем выпускает внутренний JWT
   с `credential=service-token`.
4. Сервис проверяет Ed25519 по JWKS, `iss=danysik-auth`, `aud=banwords`,
   срок и право `banwords:dictionaries:read` (либо `superadmin`). Для каталога
   и hash дополнительно обязателен маркер `credential=service-token`.

**Cookie-сессия, включая superadmin, каталог и hash не открывает.** Сессия
с правом чтения может получить только OpenAPI JSON. Подделанный клиентом
`X-Auth-Token` вырезает Caddy; внешний секрет удаляется перед proxy в сервис.
Неизвестный/недоступный путь, неверный токен или неподходящий тип доступа — 404.

Управление service-токенами работает через cookie-сессию сайта в auth:
`GET/POST /api/auth/service-tokens`, `DELETE /api/auth/service-tokens/{id}`.
Отзыв либо снятие прав блокирует следующий внешний запрос. Уже скачанные
данные остаются у клиента. Выданный внутренний JWT живёт до короткого `exp`,
но каждый новый внешний запрос заново проверяется auth.

JWKS кешируется 300 с; обновление по неизвестному kid — не чаще раза в 5 с,
параллельные запросы объединяются. Таймаут 3 с, ответ до 64 КиБ/16 ключей,
редиректы и cookie при запросе ключей запрещены. Истёкший кеш при недоступном
upstream не используется. Ошибка JWKS — 503/`Retry-After: 5`.

Лимит — 60 запросов/мин на владельца, до 10000 активных владельцев в памяти.
Превышение — 429 с `Retry-After`; методы кроме GET — 405/`Allow: GET` после
проверки доступа. Непредвиденная ошибка — 500 без подробностей. Заголовки,
токены, слова и пользовательские тексты не логируются.

## Локальный запуск и CI

```sh
make test     # race detector + 100% statements и отсутствие непокрытых блоков
make check    # go vet + gofmt
make build    # bin/banwords
./bin/banwords
./bin/banwords healthcheck
```

Переменные: `PORT` (8080), `BANWORDS_JWKS_URL`
(`http://auth:8080/.well-known/jwks.json`), `BANWORDS_DATA_DIR` (необязательный
корень с `catalog.json`; по умолчанию файл встроен в бинарник). Внешних
Go-модулей, vendor и runtime Node.js нет. Docker собирает статический бинарник
`CGO_ENABLED=0`; runtime distroless/nonroot, healthcheck — сам бинарник.

Тесты работают с локальным HTTP и подменёнными auth/JWKS, без production и
настоящего Twitch. Проверяются закрытая схема, полный функциональный каталог,
хэш всех полей и точного HTTP-тела, отсутствие доступа через сессию/суперадмина,
отмена и объединение запросов JWKS, ротация/таймауты, лимиты и graceful shutdown.

Репозиторий — `modaniru/danysik-banwords`; включённый workflow выполняет проверки
и публикует `ghcr.io/modaniru/banwords:sha-*` в GHCR. Старый SSH deploy удалён;
первичный запуск зарегистрированного ресурса выполняется через Coolify.
Для API 2.0 auth сначала должен начать выдавать JWT-маркер service-токена;
после этого выкатывается backend. Сами пользовательские service-токены
перевыпускать не требуется.
